# 環境變數

所有 env 變數的唯一總表是 repo 根的 [`env.registry.toml`](../../env.registry.toml)。
編輯它之後跑 `npm run env:gen`，即會重新產生：

- 7 個 `*.env.example` 範本
- `.github/{secrets,variables}/*.env.example` 的鍵集合（值仍手動維護）
- 本頁下方「各檔變數」區塊
- `env.manifest.json`（`scripts/env/manage.sh` 與 CI 部署讀取）

`npm run nb -- env init <dev|stg|prod>` 只建立指定環境的檔案；selector 使用短名，
檔案內的 `ENVIRONMENT` 則寫成 `development`／`staging`／`production`。
一律不提交 runtime `.env`。註記：`(選用)` 可留空、`(dev)` 僅本機直跑時需要。

`env init` 會在 `backend/shared.<env>.env` 的 `TWITCH_TOKEN_ENCRYPTION_KEY` 缺少或空白時
自動生成 Fernet key，且不覆寫既有有效值。這把 key 必須長期保留；任意輪替會讓資料庫內既有的
Twitch OAuth credential 無法解密。正式環境仍由 secret store 提供，不會由部署流程臨時生成。

> 需要 AI 功能時，至少完整設定一組 provider 的 API key 與 model；完全未啟用的 provider
> 會被跳過。優先序見 [architecture/overview.md](../architecture/overview.md) 的 AI Provider 鏈一節。

範本維持單份，實際檔名明確帶環境：

| 範本 | dev | stg | prod |
| --- | --- | --- | --- |
| `.env.example` | `.env.dev` | `.env.stg` | `.env.prod` |
| `backend/shared.env.example` | `shared.dev.env` | `shared.stg.env` | `shared.prod.env` |
| `backend/<service>/.env.example` | `.env.dev` | `.env.stg` | `.env.prod` |
| `frontend/.env.example` | `.env.dev` | Cloudflare 設定 | Cloudflare 設定 |

既有未帶環境的檔案可用 `npm run nb -- env migrate <target>` 搬移；target 必填，避免把
舊檔誤判為 dev 或 prod。搬移或手動調整後執行 `npm run nb -- env validate <target>`，
檢查 key 集合、順序、部署必填值與成組設定，不輸出值。若要按新 example 排列並把舊
service-level shared key 搬回 shared 檔，先做 snapshot，再執行
`npm run nb -- env sync <target>`；未知 key 或不同檔案的非空值衝突會在寫入前中止，錯誤訊息不含值。
`dev` validation 另要求 host DB 使用 loopback、container DB 使用 `postgres`，兩者須與
`POSTGRES_*` 一致。外部身分採 prod／nonprod 兩套：以 registry 的 `nonprod_shared` 明確列出的
bot、OAuth app 與 provider credentials 允許 dev 共用 stg 值，其餘內部 secret 必須三環境隔離，且 dev
永遠不得重用 prod 身分。執行 `npm run nb -- env sync dev --from-stg` 可安全同步白名單，不會複製
資料庫、JWT 或加密金鑰。dev 與 stg 的 bot runtime 不可同時啟動。

## Nightbot 指令匯入

後台 Commands 頁的「匯入」可以把使用者在其他機器人上的自訂指令搬過來。

- **StreamElements** 不需要任何設定，指令與各頻道的啟用狀態都是公開可讀的。
- **Nightbot** 需要 OAuth。它的未授權讀取會把變數塗銷（`$(user)` 變成 `[user]`）且
  無法還原，實測約四分之一的指令會受影響，所以這個來源一律走授權流程。

應用程式是**由維運者註冊一次**，所有實況主共用 — 他們只是授權給這個 app，不需要各自
註冊。與 Twitch 登入用的 `TWITCH_CLIENT_ID` 是同一種模式。

`NIGHTBOT_CLIENT_ID` / `NIGHTBOT_CLIENT_SECRET` 是 env-scoped，**prod 與 nonprod 各註冊
一個 app**；dev 與 stg 共用 nonprod app，但 `JWT_SECRET_KEY`、`PAYMENT_ENCRYPTION_KEY`
仍各自獨立。

設定步驟（每個環境各做一次）：

1. 到 <https://nightbot.tv/account/applications> 建立應用程式
2. Redirect URI 填 `<API_URL>/api/commands/import/nightbot/callback`。必須完全相符，
   含 scheme 與大小寫；一個 app 可以列多個，本機開發的
   `http://localhost:8000/...` 可以掛在測試區那個 app 上。
   `<API_URL>` 是該環境的 GitHub Actions variable `API_URL`（`gh variable list
   --env staging`），它指向 Cloudflare Pages 網域而非後端主機 —— Pages 會把
   `/api/*` 代理到後端，所以對外的 API origin 與前端相同
3. 產生 client secret，把兩個值填進對應環境的
   `NIGHTBOT_CLIENT_ID` / `NIGHTBOT_CLIENT_SECRET`

Nightbot 沒有審核流程，註冊完即可讓其他使用者授權。要求的 scope 是唯讀的
`commands commands_default`。取得的 access token 不會存進資料庫：在處理 callback
的那一個 request 內換取、使用、撤銷，與 `auth_router` 的 collaborator 流程相同。

## 本機覆蓋

本機開發可建 `backend/shared.dev.local.env` 覆蓋 shared 值；服務層使用
`backend/<service>/.env.dev.local`。兩者都不提交。

## CI/CD

GitHub Actions 部署值放在 `.github/secrets/{base,prod,stg}.env` 與
`.github/variables/{base,prod,stg}.env`。用 `nb env push <stg|prod>`／`pull` 同步；本機短名
會映射到 GitHub Environment `staging`／`production`。push 前會先驗證 generated drift 及四個
本機檔案的結構、必填值與成組設定，再進行任何 GitHub mutation。部署時 `_deploy.yml` 透過
`scripts/env/ci.py` 依 `env.manifest.json` 寫出 `.env.<env>` 與各服務 env。詳見
[deployment.md](deployment.md)。

- Secrets：密碼、API key、token、client secret、session cookie、webhook URL 與 Fernet key。
- Variables：公開 ID／public key、URL、model ID、狀態與其他非敏感設定。
- `base` 只放真正跨環境共用值；外部身分使用 `stg`（nonprod）／`prod` 兩套，資料庫與內部加密
  金鑰則維持 dev／stg／prod 三套。
- `# KEY=` 是未啟用的選用值；移除 `# ` 並填值才會推送。AI 與 Nightbot 必須整組設定。
